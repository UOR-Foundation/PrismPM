# PrismPM Specification

This document is the normative specification for PrismPM.

## 1. Repository, scope, and project configuration

PrismPM validates a repository-authored formal profile for information systems
across multiple viewpoints:
- **ISO/IEC/IEEE 42010:2022**: Systems and software engineering — Architecture description.
- **ISO/IEC 27034-1:2011 & ISO/IEC 27034-5:2017**: Information technology — Application security.
- **ISO/IEC 27005:2022**: Information security risk management.
- **ISO/IEC 25010:2023**: Systems and software product quality model.

The exact standards rows, editions, public-catalog or authorized-review scope,
and original interpretations are in `model/standards.toml`. PrismPM does not
reproduce a standard, grant certification, or prove facts asserted by a
standard. ISO/IEC 25019, ISO/IEC 27034 parts other than 1 and 5, quality-in-use
outcomes, and organizational certification are outside version 0.1.0.

The only supported and normative host for version 0.1.0 is
`x86_64-unknown-linux-gnu`. Rust 1.97.1 and Lean 4.32.1 are mandatory. Tool
installer identities and the supported-host list are closed by `tools.lock`.

### 1.1 Project configuration

`prismpm.toml` is UTF-8 TOML with exactly this closed shape:

```toml
spec = "prismpm/project/1"
project = "nonempty display name"
lexlean_project = "lexlean.toml"
build_root = ".prism"

[limits]
max_holo_bytes = 16777216
max_entities = 100000
max_diagnostics = 256
```

All five top-level fields and all three limit fields are required; unknown
fields are errors. The three limits are positive and capped respectively at
1,073,741,824 bytes, 10,000,000 entities, and 10,000 diagnostics.
`lexlean_project`, `build_root`, and an optional CLI `--config` are confined,
nonempty, slash-separated project-relative paths whose components use ASCII
letters, digits, dot, hyphen, and underscore, never `.` or `..`. `build_root`
is exactly one directory-name component, so cleanup can never select the
project root or traverse an intermediate directory.
Existing configured input paths must contain no symlink. The output root must
not be a symlink. Configuration cannot select language backends, verifier
stages, toolchains, standards, runtime roots, or dependency revisions.

### 1.2 Formal-source and dependency boundary

Every Prism-owned formal type, value, validator, proposition, theorem, and
proof is authored in `.lex.tex` and generated by LexLean. Handwritten Prism
`.lean`, `lakefile.lean`, Lean wrappers, exporter modules, tactics, raw Lean
payloads, and selectable compiler backends are forbidden. Generated Lean is a
build artifact or a manifest-owned reviewed golden, never authoritative source.
The immutable LexLean and `lean4-prod` revisions and source/crate hashes are in
`model/dependencies.toml`; adjacent repositories and mutable references are not
dependencies.

### 1.3 Compiler pipeline

PrismPM operates through a verification-oriented multi-stage pipeline:
1. Systems and facets are authored in `.lex.tex` using LexLean 1.1 lexicons.
2. LexLean lowers the model to Lean 4 for formal verification (`leanchecker` and axiom audit).
3. The Prism Holo emitter produces canonical `prismpm/holo/1` artifacts from LexLean semantic snapshots.
4. `lean4-prod` extracts compilable LCNF from the verified Lean declarations and emits `kernel.ir`.
5. `prod-codegen` compiles `no_std` Rust validators that perform no heap allocation during validator calls and execute over normalized Holo models.

`check` ends after in-memory snapshot projection and validation. `build` adds
deterministic platform-independent artifacts but makes no verification claim.
Only `verify` runs Lean, `leanchecker`, axiom audit, LCNF extraction, Rust
generation, compilation, and execution.

## 2. Facet packages and formal metamodel

The product facet names `prism-arch`, `prism-sec`, and `prism-qual` correspond
to the legal LexLean package IDs `prism.arch@1.0.0`, `prism.sec@1.0.0`, and
`prism.qual@1.0.0`. They use language 1.1, exact local package locks, and only
the language-1.1 builtin packages. Each public surface has one owner. Import,
denotation, and ownership graphs are acyclic and unambiguous; every renderer
atom and signature is closed by its package.

`Foundation.Arch` owns architecture data, `Foundation.Sec` owns security and
risk data, `Foundation.Qual` owns product-quality data, and `Foundation.Holo`
owns cross-facet normalized validation inputs. Entries identify declarations
through qualified LexLean document denotations, never external Lean names.
`model/projection.toml` is the closed mapping from declaration data to Holo
catalog/entity arrays. An unmapped declaration is valid LexLean content but is
not silently projected.

The fixed runtime root set and sorted Lean names are in
`model/runtime-roots.toml`. Runtime validity is separate from any erased `Prop`
field. Generated validators operate on monomorphic `Nat`, Boolean, enum,
structure, and list data admitted by `lean4-prod`; JSON, string sorting, and
checked host boundary conversion are not attributed to them. The root set also
contains `canonicalIndexes` so the supported caller-owned list-return buffer
and its exact exhaustion error are exercised; the host remains responsible for
sorting external IDs before assigning indexes.

## 3. Canonical Holo contract

A Holo artifact is exactly one UTF-8 JSON value with schema
`prismpm/holo/1`. Its top level has exactly `architecture`, `provenance`,
`quality`, `schema`, `security`, and `standards_profile`. DTOs reject unknown
fields. Numbers are nonnegative JSON integers representable as `u64`; floats,
duplicate object names, invalid UTF-8, trailing bytes, insignificant
whitespace, and noncanonical escaping are rejected.

Canonical JSON sorts object keys by ASCII byte order, writes arrays in their
schema-defined order, uses minimal escaping, writes decimal integers without
leading zeroes, and has no final LF. The Holo ID is lowercase hexadecimal
SHA-256 of those exact bytes and is not embedded in the document. Strict decode
first parses and validates the value, canonically re-encodes it, and rejects a
byte mismatch; diagnostic `PP3002` includes the canonical spelling as a note.

Every entity ID has `<logical-module>::<component-id>` form. Catalog IDs are
qualified facet entry IDs. Entity and catalog arrays are sorted by ASCII ID,
unique, and assigned consecutive zero-based indexes after sorting. All index
references must address the corresponding array; component graph cycles are
legal. The standards profile is exactly the five registered editions:
42010:2022, 27034-1:2011, 27034-5:2017, 27005:2022, and 25010:2023.

`Foundation.Holo.canonicalIndexes expected count` recursively denotes the
single consecutive list of `count` natural indexes beginning at `expected`.
`canonicalIndexAssignment count values` is the proposition that `values`
equals `canonicalIndexes 0 count`; the generated
`canonicalIndexAssignmentUnique` theorem characterizes the proposition by
that equality. This is the formal uniqueness boundary. Sorting external string
IDs and checking their conversion to `u64` remain host responsibilities.

Provenance contains LexLean `source_id`, `semantic_id`,
`compiler_semantics_id`, semantic `snapshot_id`, Prism
`emitter_semantics_id`, and the sorted exact facet package/version/content-ID
closure. These IDs are 64-byte lowercase hexadecimal SHA-256 strings. The
emitter-semantics ID is the canonical length-delimited tree digest of exactly
the files listed in `model/emitter-inputs.toml`; the list and stored digest are
audited together. Holo contains no timestamp, host, output path, random value,
or verification status.

## 4. Controller API, CLI, and diagnostics

The public API consists of `Controller::load`, `check`, `build`, `verify`, and `clean`
with owned request/result types. Requests contain only an optional confined
configuration path. Results use schemas `prismpm/check-result/1`,
`prismpm/build-result/1`, and `prismpm/verify-result/1`. No public type exposes
LexLean mutable IR or `lean4-prod` internal IR.

The CLI grammar is:

```text
prismpm [--project PATH] [--config RELATIVE_PATH] [--json]
        <check|build|verify|clean>
```

`--project` defaults to the current directory. With `--json`, success emits
exactly one canonical JSON value plus LF on stdout; failure emits exactly one
`prismpm/error-result/1` envelope plus LF on stdout. Human success uses one
line on stdout and human failure uses stderr. Exit 0 means success, exit 2 is
CLI/configuration failure, exit 101 is `PP9001`, and all other registered
diagnostics exit 1. `clean` removes only the configured real output directory
and returns `prismpm/clean-result/1`.

`PrismError` is closed by `model/errors.toml` and carries a code, stable
message, optional primary byte/line/column span, ordered labels, ordered notes,
ordered help, and ordered structured causes. A LexLean cause retains its
subsystem code and structured locations; Rust debug formatting is not part of
the contract. User-controlled input must produce a registered diagnostic and
must not panic.

## 5. Prism-stdlib contract

The root LexLean project selects language 1.1, `stdlib/src/System.lex.tex` as
its entrypoint, and the three exact path facet packages. Foundation modules
define the fixed standards profile; architecture, security/risk, quality, and
Holo types; View/Viewpoint classes and instances; normalized inputs; recursive
Boolean validators; their propositions; soundness/completeness theorems; and
canonical index uniqueness. `System` provides at least one value of every
release type and coherent architecture, viewpoint, risk/control, and quality
chains. Its graph deliberately contains a legal cycle.

All Prism theorem policies are empty. Verification acceptance requires Lean
elaboration, same-toolchain `leanchecker` replay, and an exact empty observed
axiom array for every generated `PrismPM.*` declaration. Goldens are reviewed
output, never a substitute for direct verification.

## 6. Build artifacts and identities

`check` loads LexLean, obtains `lexlean/semantic-snapshot/1`, projects and
validates Holo entirely in memory, enforces configured limits, and writes
nothing. It does not launch Lean, Lake, `leanchecker`, `lean4-prod`, rustfmt,
rustc, or a generated executable.

`build` invokes LexLean's deterministic build and publishes under
`<build_root>/build/<prism-build-id>/`. The fixed tree contains `model.holo`,
`lexlean/snapshot.json`, every selected LexLean manifest/module Lean/LaTeX/map/
coverage/lexicon-closure artifact below `lexlean/build/`, and
`manifest.json`. The manifest schema is `prismpm/build-manifest/1`; each file
row contains its relative path, closed kind, byte length, and SHA-256.

The Prism build ID is SHA-256 of canonical `prismpm/build-inputs/1` bytes
containing LexLean source, semantic, and build IDs, Holo ID,
emitter-semantics ID, and dependency-register digest. Paths and environment do
not participate. Publication takes an exclusive lock, writes a unique staging
directory with create-new semantics, synchronizes it, and atomically renames
it. An existing build is reused only after its exact file set, types, and bytes
match; extra files, symlinks, missing files, and tampering are errors.

## 7. Named export and bounded execution

`verify` requests the sorted roots in `model/runtime-roots.toml` through
`prod-export --module ... --root ... --ir-module ... --out ...`. Requested
roots and their deterministic transitive compilable closure must contain no
opaque node, unsupported type, or unresolved external call. Two exports in the
same run must produce byte-identical `kernel.ir`, `roots.json`, and
`coverage.json`. `prod-ir` parses the entire LCNF file and `prod-codegen`
generates byte-identical Rust twice before pinned rustfmt and optimized rustc
compilation.

The host decodes canonical Holo, validates provenance/profile/references,
normalizes IDs to checked `u64` indexes, and calls generated validators. The
validator-call interval is measured by the shared allocation counter and must
not allocate. All returned `Result` values are checked; overflow and output
exhaustion are failures, never wrapping behavior.

Execution evidence has exactly schema `prismpm/execution-evidence/1`, status
`passed`, strategy `exhaustive-v1+lcg-v1`, seed `5eedcafef00dbeef`, 597 cases,
maximum list length 16, and value domain `u64`, with `no_allocation` and
`no_panic` true. It also records the SHA-256 of the exact typed
`model/execution-corpus.toml` bytes. That register fixes all bounds and counts,
binds every executed root or helper to its fully qualified LexLean-generated
soundness/completeness or uniqueness theorem, and has a runtime-root subset
exactly equal to `model/runtime-roots.toml`. Every listed theorem must have an
exact empty observed axiom set in the accepted LexLean attestation. The 85
exhaustive input cases enumerate all lists of lengths 0
through 3 over values 0 through 3 for every registered validator, helper,
canonical-index generator, and standards-profile truth table. Each case
exercises multiple oracle-bound checks. The
remaining 512 deterministic LCG cases cover lengths 0
through 16, invalid references, empty data, `u64::MAX`, and checked overflow.
The evidence records `shrink_result = \"not-applicable-passed\"`, because no
counterexample exists to shrink. This is a fixed finite strategy, not
unconstrained fuzzing or a universal claim.

## 8. Verification and attestation

Every child is launched directly, never through a shell, with environment
cleared except the minimum pinned tool homes/path plus an explicit `LEAN_PATH`
for named export. Each child has a 300-second timeout, TERM then a five-second
KILL grace period, and independent 16,777,216-byte stdout/stderr limits.
Process records contain normalized arguments/output, exit status, and SHA-256
of the executable bytes. Timeout, signal, overflow, malformed output, nonzero
exit, or missing executable is a registered failure.
Normalization replaces confined absolute roots with fixed tokens, converts
line endings to LF, replaces Lake build durations with `<DURATION>`, removes
Lake's schedule-dependent `[job/total]` progress ordinals, and sorts the
remaining successful Lake progress lines bytewise. It does not erase errors,
warnings, tool identities, arguments, or exit status.

Verification first completes and validates LexLean verification. It accepts
only a `verified` attestation, validates the attested build-manifest hash, and
stages only exact attested generated Lean paths whose sizes and hashes match.
The confined temporary workspace has generated modules plus declarative
`lakefile.toml` and `lean-toolchain`; it has no Prism-authored `.lean` adapter.
It builds generated modules, replays every module with `leanchecker`, checks
the LexLean declaration audit, unpacks the pinned `lean4-prod` Lean source,
runs named export, code generation, compilation, and the execution corpus.
No verification stage updates dependencies or accesses the network.

The canonical `prismpm/verification-manifest/1` binds build and LexLean
attestation IDs, runtime roots, normalized process records, execution evidence,
and sizes/hashes of Holo, LexLean attestation, coverage, roots, LCNF, the typed
execution-corpus register, execution evidence, generated Rust, and executable.
The attestation ID is SHA-256 of manifest bytes; the
manifest does not contain its own ID. Only after all stages pass are the
manifest and normalized platform-independent evidence atomically published at
`<build_root>/verified/<attestation-id>/`. Failed verification publishes no
verified directory.

## 9. Security, acceptance, and release

All source/config/package inputs are confined regular files. Symlinks,
absolute paths, traversal, hidden adjacent dependencies, generated source in
the repository, handwritten Lean, unsafe Rust, unregistered public errors,
unbounded child output, and mutable dependency references are rejected. Build
and verification are offline. Canonical platform-independent artifacts contain
no absolute checkout path, hostname, locale text, random identifier, timestamp,
or traversal-order dependence.

`cargo xtask vv` is the sole normative acceptance entry point and `just vv` is
its alias. It performs these 14 non-mutating gates in order: formatting; model,
diagnostic, standards, and generated-document validation; SPEC/register/
scenario/test links; source/error/unsafe/dependency/generated-file audits;
Clippy with warnings denied; workspace unit and property tests; conformance and
negative fixtures; generated Lean build/replay/axiom/source audits; LexLean
format/lock plus Prism check/build/verify; Holo schema and reviewed goldens;
named export/coverage/Rust/execution evidence; two-root reproducibility;
dependency policy; and packaged-crate/downstream-API checks. Golden and fixture
rewriting require separate explicit commands and a review reason. Linux CI
runs that exact command in the pinned devcontainer. Acceptance evidence is
canonical `prismpm/vv-evidence/1`, lists all 14 gates, records `passed`, and
binds the exact full Git commit.

Release version 0.1.0 requires a clean exact commit, byte-current generated
documents and goldens, all release-scope capabilities/standards implemented,
no open measurement used for acceptance, a dated changelog, exact dependency
revisions/checksums, complete exact-commit `vv` evidence, reproducible source
archive, canonical dependency SBOM, release manifest, and SHA-256 list. The
release assembler builds twice and refuses differing bytes. No release tag or
artifact is evidence for a different source commit.
